上周，我通过 Vibe Coding 得到了一个能够运行的 JobPilot 原型，也发现直接通过整个大项目来学习有些力不从心。代码规模增长得太快以后，普通的整仓总结很难让我真正理解语法怎么使用、接口为什么这样设计，以及出现问题时应该修改哪里。

所以这周没有继续给 JobPilot 增加大量功能，而是开始验证另一条路线：把项目拆成一门适合自己学习的后端复现课程，通过源码阅读、隔离实验、运行验证和逐步复现，一块一块把项目重新学回来。

这周最终没有完成一条完整的 JobPilot 业务链路，但把原本比较模糊的“从零复现”想法变成了可以执行的课程，完成了 Eino 模型流、Agent 与 Tool、Embedding 与 pgvector 三个技术探针，也在实际使用中继续调整了 AI 教学方式。

目前的结论是：这套方式确实能让我学得更深入，但它还没有完成最终验证。学习速度比预想中慢，教学流程也需要边用边改，不过至少学习开始有了一些进展。

## 从大型仓库转向后端复现课程

我把 JobPilot 后端按学习依赖拆成了多个阶段：先验证模型调用、Agent、向量检索和 SSE 等核心技术，再进入正式工程骨架、目标岗位、JD 与 RAG、个人画像、GitHub 仓库审计、Copilot Agent 以及最终测试与交付。

每个阶段继续拆成更小的课时。每次只学习一个相对独立的问题，并提前写清学习内容和验收方式。学习结束后，再把自己真正理解的内容、运行结果和仍然存在的边界记录到滴答清单评论里。

为了让 AI 按顺序引导课程，我也继续调整了 `dida-next-lesson` Skill。理想中的流程是：

```text
读取下一节未完成课时
        ↓
明确本节目标和已有基础
        ↓
沿真实源码或隔离实验逐步学习
        ↓
运行测试、真实入口或错误场景
        ↓
记录理解、证据和边界
```

实际使用没有这么顺利。最初的教学内容仍然不完全适合我的节奏：有时一次讲得太多，有时过早进入低收益的测试细节，也可能把“AI 已经解释完”误当成“我已经学会”。直到 1.3 课时，我一边学习一边调整规则，整个过程才逐渐变得更可用。

这也说明，大型仓库学习 Skill 不是提前写好一套万能提示词就结束了。它更像一个需要根据真实学习反馈持续调整的教学工具。

## 先用教程补齐 Eino 基础

8 月 18 日至 19 日，我系统看完了[《Go Agent 实战指南》中的 Eino 框架基础](https://golangstar.cn/go_agent_series/eino_basic/eino_overview.html)，内容覆盖框架结构、ChatModel、Prompt 与消息、Tool 以及 ReAct Agent。

这部分理论铺垫很有帮助。后面进入课程实验时，ChatModel、Message、Tool Call、Tool Result 和 ReAct 循环已经不再是完全陌生的概念，源码学习轻松了不少。

不过，我也发现教程与当前课程使用的 Agent 接口并不相同。教程的 ReAct 示例使用的是：

```go
github.com/cloudwego/eino/flow/agent/react
react.NewAgent(...)
agent.Generate(...)
agent.Stream(...)
```

而 JobPilot 复现课程学习的是 Eino ADK 路径，主要涉及：

```go
github.com/cloudwego/eino/adk
adk.NewChatModelAgent(...)
adk.Runner
adk.AgentEvent
```

两套接口背后的核心逻辑没有变：模型决定是否调用 Tool，Tool 执行结果重新进入上下文，模型继续推理，直到生成最终回答。但 Agent 的配置、执行入口、流式事件和扩展方式已经不同。

旧的 `flow/agent/react` 路径目前仍保留在 Eino 官方文档中，不能简单说它已经完全不可用；但对于 JobPilot 当前使用的依赖和后续扩展，具体实现仍应以 ADK 官方文档、当前版本源码和实际编译结果为准。

这次经历让我更明确了第三方教程的定位：教程适合建立概念和快速入门，但对于仍在快速演进的框架，具体 API 不能只凭教程记忆。稳定的设计思想可以迁移，容易变化的类型、配置和调用方法则必须回到官方资料核对。

## 1.1：Eino ChatModel 流式调用

第一课围绕 ChatModel 的流式调用展开，主要学习了 `ChatModel`、`Message`、`Stream`、`Recv`、`io.EOF` 和 `Close` 之间的关系。

以前容易把所有“流式输出”都看成同一件事，这次进一步区分了几个不同层次：

- 网络传输中的分片；
- Eino 返回的 Message chunk；
- 模型内部生成的 token；
- 最终提供给浏览器的 SSE 事件。

它们之间可能存在对应关系，但并不是同一个概念，也不一定一一对应。服务端拿到一个 Message chunk 后，还可能重新组合成自己的 `status`、`delta`、`error` 和 `done` 事件。

错误同样需要分层处理。调用 `Stream` 时就失败，说明流还没有成功建立；流已经建立以后，`Recv` 仍可能因为网络、模型服务或超时而中途失败。正常读完则通过 `io.EOF` 表示结束，不能把它当作普通错误处理。

我也理解了外层业务 `context` 和模型客户端超时之间的关系。它们相当于嵌套的生命周期约束，实际调用会在更早的截止时间到来时停止。浏览器取消、服务端超时和模型客户端超时虽然都可能让请求结束，但来源和后续处理并不相同。

## 1.2：单 Agent 与 Tool

第二课围绕一个只有单个 Tool 的 Agent 隔离实验展开。这部分没有继续追求复杂 Agent，而是把最基本的循环彻底拆开：

```text
模型第一次生成 Tool Call
        ↓
ToolsNode 解析参数并执行 Tool
        ↓
Tool Result 写回消息历史
        ↓
模型第二次生成最终回答
```

如果模型判断不需要调用 Tool，就直接生成回答，不进入工具执行阶段。

这次重点理解了不同校验层的职责。JSON 类型错误会在解码阶段失败；字段缺失和数值越界属于业务校验。对于数值字段，如果使用普通 `int`，缺失和合法的 `0` 在解码后可能无法区分，因此可以使用指针让 `nil` 明确表示字段没有提供。

隔离实验覆盖了正常调用、无需调用 Tool、缺字段、类型错误和越界等场景。`go test ./...` 通过；离线入口中，正常场景发生一次 Tool Call 并成功执行一次，无需 Tool 的场景为零次调用，三个非法参数场景都能在预期位置失败。

我还进一步理解了有副作用 Tool 的重试边界。查询类 Tool 重复执行通常问题不大，但确认、写入和删除等操作如果在超时后盲目重试，可能造成重复副作用。JobPilot 需要通过稳定的 `action.ID` 和 `pending → executing → confirmed` 等状态转换，区分“没有执行”“正在执行”和“已经确认”，而不能只依靠模型再次发起调用。

这一课的边界也很明确：我主要完成了源码阅读和已有实验的运行验证，没有重新调用真实模型，也没有为了凑成果增加低收益的小测试，因此目前缺少新的独立代码修改证据。

## 1.3：Embedding 与 pgvector

第三课围绕 Embedding、PostgreSQL 和 pgvector 展开。这一课的真实运行证据最完整。

我沿着配置、样例数据、Embedding 适配器、离线替身、数据库和主入口学习了完整的数据流：文本先通过同一个模型转换为向量，Go 代码检查维度，随后写入 PostgreSQL 的 `vector(1024)` 列，查询文本也通过相同模型生成向量，最后计算 Top-K 相似结果。

这里最重要的是端到端维度契约。Embedding 模型输出、Go 代码预期和数据库列维度必须完全一致。只要其中一层从 1024 变成 1536，系统就不应该继续运行，更不能静默截断或填充向量。本次实验已经验证 1536/1024 不匹配会在写入前明确失败。

距离语义也需要说清楚。pgvector 的 `<=>` 返回余弦距离，距离越小越接近；如果要显示通常理解的余弦相似度，需要使用 `1 - 距离`。

本次使用百炼 `text-embedding-v4` 进行了真实小流量验证，JD 和查询均生成 1024 维向量，6 份脱敏 JD 成功写入。一次真实查询得到的 Top-3 为：

| 排名 | JD | 余弦相似度 |
| --- | --- | ---: |
| 1 | AI 应用后端 | 0.923652 |
| 2 | Go 后端 | 0.729510 |
| 3 | Java 后端 | 0.574180 |

实验也验证了 HNSW 索引可以被查询计划使用，但只有 6 行数据时，PostgreSQL 选择顺序扫描很正常。HNSW 解决的是大量向量中的近邻检索效率，并不理解文本本身，也不保证在极小数据集上比顺序扫描更合算。

另外，线上模型失败时不能为了让流程看起来成功而静默切换到离线替身。离线 Embedder 适合普通测试和本地验证，但真实入口应该明确暴露模型不可用，否则测试通过会掩盖生产链路已经失效。

## 这套学习方式是否有效

和直接阅读整个 JobPilot 相比，拆成课时和隔离实验以后，我确实更容易看清一个技术点的输入、输出、依赖和失败场景。滴答评论也让我能够在每课结束后留下可核对的学习记录，而不是几天以后只记得“好像看过”。

教程、源码和实验之间也逐渐形成了分工：

- 教程负责建立框架概念和整体直觉；
- 官方文档与当前源码负责确认真实接口；
- 隔离实验负责证明技术链路能够运行；
- 课程评论负责记录我到底理解了什么；

但按照上周制定的验收标准，本周目标只能算部分完成。

原计划希望至少掌握一条完整的 JobPilot 纵向链路，并能够脱离原代码完成一个小修改。实际只完成了阶段 1 四个技术探针中的前三个，React → Gin → POST SSE 仍未完成；当前内容也主要是相互隔离的技术验证，还没有进入正式业务链路。特别是 1.2，目前只有阅读和运行证据，没有独立修改证据。

本周的有效学习时间也不连续。教程探索、教学流程调整和滴答 MCP 修复占用了一部分时间，另外还有配镜和家庭事务带来的中断。课程战线因此比预想中更长，但换来的好处是每一课真正学到的内容更多，也更容易暴露理解上的空缺。

所以目前最合适的结论不是“这种方法已经成功”，而是：**方向值得继续，教学流程已经开始可用，但还需要用完整链路和独立修改做进一步验证。**

这些题仍然采用“先尝试，再参考题解理解，后续多轮手写复现”的方式。二叉搜索树的中序有序性质、逆先序展开和树上前缀和等思路，本轮都不同程度依赖了题解提示。因此 AC 只能证明已经完成本轮理解和代码验证，不能直接等同于面试时能够稳定独立写出。

相比继续刷新题，下阶段更重要的是隔一段时间重新手写，并能够解释递归函数的输入、返回值、遍历顺序、状态恢复和复杂度。

## 写在最后

上周的问题是：AI 能够很快写出一个大型项目，但我怎样才能把这些代码真正学回来？

这周还没有给出完整答案，但至少找到了一个更具体的方向。把仓库拆成课程、把课程拆成实验、再用运行证据和正式业务链路验收，确实比让 AI 一次讲完整个项目更接近真正的学习。

这个过程没有 Vibe Coding 生成整个项目那么快，甚至比我一开始预想得慢很多。但对一个最终要写进简历、接受面试追问并继续维护的项目来说，速度不是唯一指标。能够解释接口、识别版本差异、验证失败路径，并在 AI 无法继续处理时知道应该从哪里下手，才是我真正需要建立的掌控力。

下周先完成最后一个技术探针，再进入正式工程，争取跑通 JobPilot 的第一条真实业务纵向链路。相比继续停留在相互隔离的实验里，阶段 2 会进一步检验这些技术能否真正组合成一个可运行、可解释的后端系统。
