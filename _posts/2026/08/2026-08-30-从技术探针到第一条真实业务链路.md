## 阶段 1 收口：React → Gin → POST SSE

阶段 1 的最后一课是把之前单独验证过的模型流、Agent 与 Tool 接到浏览器上。

本课只保留必要的前端内容，没有扩展复杂页面。前端通过 `fetch` 发送 POST JSON，使用 `ReadableStream` 读取响应，并缓存尚未形成完整 SSE 事件的分片；服务端则把 Agent 运行过程转换为 `status`、`delta`、`error` 和 `done` 等事件。

完整链路可以概括为：

```text
React 发起 POST 请求
        ↓
Gin Handler 建立 SSE 响应
        ↓
Eino Agent 调用模型
        ↓
模型生成 Tool Call
        ↓
Tool 执行并回填 Tool Result
        ↓
模型生成正文增量
        ↓
Gin 发送 delta 与 done
        ↓
前端解析并显示
```

这次进一步区分了几类事件：`tool_call` 是模型提出的调用请求，`tool_result` 是工具执行结果，`delta` 是最终回答的正文增量，`done` 只表示正常结束。它们不能混在一起，也不能把收到 Tool Result 误认为整次 Agent 已经完成。

错误边界同样重要。SSE 首次 Flush 以后，HTTP 200 已经提交；后续模型失败不能再把状态码改成 500，只能通过流中的 `error` 事件告诉前端。浏览器主动取消时，请求 Context 和 Agent 运行 Context 会一起取消，连接已经不可写；服务端自己的超时则只会让运行 Context 结束，请求连接仍可能有机会发送一个安全的超时事件。

最终完成了 Go 端 10 项测试、前端 2 项分片解析测试和 Vite 构建，并在浏览器中验证正常 Tool 链路、流中模型错误和慢请求取消。Go 日志也确认取消信号已经传播到 ChatModel。至此，阶段 1 的四个技术探针全部完成。

## 阶段 2：建立正式工程骨架

如果说阶段 1 回答的是“这些技术能不能工作”，那么阶段 2 要回答的是“它们能不能组成一个结构清楚、能够继续开发的后端系统”。

这次没有继续修改最初的大型原型，而是在独立的 `jobpilot-rebuild` 中重新建立工程。阶段 2 一共包含六个课时，最终目标是跑通“目标岗位”第一条完整业务链路。

### 2.1～2.2：工程边界、测试与配置

首先建立 Go Module、`cmd/server` 组合根、业务模块、适配层和 `shared` 边界。组合根负责选择并组装具体实现，业务层只依赖 Repository、Parser 和外部客户端等接口，不直接依赖 PostgreSQL、Gin、GORM 或 Eino。

这一课让我开始更具体地理解构造函数注入和 Fake 的作用。Fake 不只是为了让测试更容易写，它还能证明业务代码是否真的脱离了数据库、模型和第三方客户端。依赖测试进一步禁止业务包反向导入具体适配层，防止分层随着项目增长慢慢失效。

在最小链路中，完成了“保存目标岗位”和“按照 JD ID 获取原文、解析、组装分析并保存”两条流程。`go run ./cmd/server` 可以运行，`go test ./...` 通过，Fake 覆盖正常路径、空目标、缺少依赖，以及 Parser 失败时不得保存半成品等场景。

随后处理配置与密钥边界，串清环境变量、默认值、配置校验、Secret 包装、日志脱敏和组合根选择 Parser 的过程。

这里重点区分了两个概念：显式离线 Fixture 是开发者主动选择的测试或演示实现；模型没有配置时的 Unavailable 适配器则应该明确失败。缺少真实密钥时，系统返回 `ErrModelUnavailable`，Import 中止且不会保存分析结果，不能为了让流程看起来成功而偷偷切换到离线数据。

最终验证了离线模式正常退出、缺少模型配置和非法日志级别启动失败，并确认错误信息不会回显密钥或非法配置值。

### 2.3～2.4：PostgreSQL、Migration 与 Web 层

数据库部分完成了 PostgreSQL 连接与 `PingContext`、GORM CRUD、事务回滚、Goose 版本化 SQL、pgvector 扩展以及 `application_metadata` 中的向量维度契约。

以前在 Go Todo 中使用过 GORM 和 AutoMigrate，但这次进一步理解了正式工程为什么更适合使用 Goose：Schema 变化应该能够被审查、追踪和重复执行，而不是在程序启动时由 ORM 隐式决定数据库结构。

实验验证了空数据库首次初始化、重复初始化幂等，以及数据库记录 1024 维而运行时配置为 1536 维时拒绝启动。系统只检查并拒绝不一致，不会悄悄改写数据库元数据。

Web 层随后加入 Gin Router、目标岗位 Handler、统一 API 错误、`trace_id` 中间件以及 live/ready 健康检查。这里重新明确了三层职责：

- Handler 负责 HTTP 参数、状态码和响应；
- Service 负责业务规则和错误语义；
- Repository 负责持久化，不参与 HTTP 表达。

实际启动后验证了 live/ready 返回 200、合法目标保存返回 200、非法 JSON 返回 400、空岗位方向返回 422。当 Service 发现目标只有空白字符时，会在调用 Repository 以前直接返回业务错误，原有数据保持不变。数据库不可用时，ready 返回 503，而 live 仍只表示当前进程存活。

### 2.5～2.6：日志、Context 与第一条业务链路

这一部分让我修正了一个关于错误和日志的误解。

我原来认为业务的每一层都可能报错，因此每一层都应该依赖日志器并立即记录。但这样会让同一个错误从 Repository、Service 到 Handler 被重复输出。更合理的做法通常是：下层使用 `%w` 等方式补充错误语义并向上传递，在 HTTP、后台任务或进程入口等有完整上下文的边界统一记录。

本课实现了 `trace_id` 的校验、生成与响应透传，并把它写入标准 `context.Context`，供业务链路和日志共同使用。同时增加 Context 愿知的 JSON 日志、按状态分级的 access log 和 panic Recovery。

运行验证确认：同一个 `trace_id` 会出现在响应和日志中；panic 返回安全的 500，不泄露底层错误、query 或 header；客户端取消能够传播到 Target Repository，readiness 超时能够传播到数据库 Pinger。这里也明确了一个边界：敏感 query 不泄漏，首先依靠的是根本不把它写进日志，而不是写入以后再期待脱敏函数兜底。

最后，阶段 2 跑通了第一条正式纵向链路：

```text
前端最小表单
        ↓
Gin Handler
        ↓
Target Service
        ↓
PostgreSQL Repository
        ↓
目标岗位持久化
        ↓
页面刷新后重新读取
```

目标表通过 Migration 建立，Service 会拒绝空白岗位方向，Repository 使用 GORM 写入和读取 PostgreSQL，前端 API Client 和最小表单完成保存与回显。用户没有提供的可选字段继续保持空值，不由系统擅自补全。

本次实际验证了成功保存、刷新后读取以及空目标返回 422 且不写库。还增加了临时 Compose app profile，可以同时启动 PostgreSQL、Gin 和 Vite。至此，阶段 2 的六个课时全部完成。

## 阶段 3：业务复杂度开始超过代码可读性

阶段 2 主要是工程骨架和一条相对简单的目标岗位链路。进入阶段 3 后，JobPilot 开始处理 JD、后台任务、证据、Embedding、检索、语义归一和市场画像，业务复杂度明显上升。

### 已完成的 3.1 市场领域模型

3.1 使用固定 JD 串联了 Document、Job、Evidence、Concept 和 Profile。

原始 JD 是可以重新分析的事实来源，因此必须保留；Evidence 保存从原文中提取出的要求以及来源 DocumentID；Concept 用统一 ID 表达 Go、Golang、Go 语言等同一能力，同时保留原始名称；Profile 则按照包含某项能力的不同来源 JD 数量统计，而不是按照证据条数重复计数。

后台分析也不应该在导入瞬间假装完成。Document 和 Job 最初处于 `pending`，Worker 开始处理后进入 `processing/running`，成功以后才变成 `ready/succeeded`。模型失败时保留原文和安全的失败状态，不产生半成品 Evidence、Profile 或虚假成功记录。

成功、模型不可用、非法状态和混合概念等测试均已通过。到这里，市场领域的主要实体、状态和关系已经形成初步结构。

### 没有完成的 3.2 JD 导入

3.2 需要同时处理表单粘贴、JSON、CSV、TXT、文本标准化、内容哈希、重复正文以及非 JD 文本拒绝。业务稍微复杂以后，我再次感到代码开始难以阅读。

打开 `market` 目录时，大量文件和防御性分支让我很难快速判断每个文件负责什么。部分代码反复处理假设中的特殊情况，主流程反而被淹没。虽然这种实现看起来考虑得很全面，但如果维护者无法迅速找到导入入口、领域规则和持久化边界，它就不一定是适合当前项目的结构。

因此，我先让 AI 重新整理了业务文件，把导入和分析职责进一步拆开。这个调整占用了一些时间，而且目前尚未形成稳定提交，所以 3.2 本周不能算完成。

这也是本周最重要的新问题：**防御性并不天然等于工程质量。** 边界处理必须存在，但如果为了提前覆盖所有想象中的异常，让核心业务被大量层次和分支包围，代码即使测试通过，也可能变得难以学习和维护。

## 本周对测试和代码结构的新认识

这周的课时推进很快，但真正有价值的内容不只是又接触了几个库。

第一，测试不只是验证输出。Fake、依赖测试、数据库集成测试和 HTTP 测试分别保护不同契约：业务规则是否正确、依赖方向是否稳定、Migration 是否可重复、Web 协议是否符合预期。如果测试只盯着一个最终返回值，就很难保护系统结构。

第二，错误语义和日志记录不是一回事。下层负责说明失败发生在哪里，上层在拥有 trace、请求或任务上下文时决定怎样记录和暴露。每层都打印日志反而会制造噪声。

第三，目录数量和抽象层次不是越多越好。接口、适配层和防御代码的价值，取决于它们是否让核心流程更容易理解和替换。如果一个模块必须先读十几个文件才能知道入口在哪里，那么即使每个文件单独看都“很规范”，整体设计也可能不适合当前规模。

第四，给代码补学习注释确实能够帮助理解，但注释不能替代清晰结构。好的结构应该让主要类型和调用方向本身就比较明显，注释重点说明设计理由、边界和容易误解的地方，而不是为每一行普通语法翻译中文。

## 下周计划

下周不直接要求完成整个阶段 3。这个阶段还包括持久化任务、Worker、严格模型解析、证据向量化、混合检索、语义归一和市场画像，复杂度明显高于阶段 2。

下一周只保留一个主目标：**在保持代码可读的前提下，完成 JD 导入和持久化任务基础链路。**

具体范围是：

1. 先完成当前市场模块重组，明确 `intake`、`analysis`、领域实体和适配器分别负责什么。
2. 完成 3.2 的预览、导入、标准化、内容哈希、去重和非 JD 输入拒绝。
3. 完成 3.3 的 Repository、事务和持久化任务表，确保 JD 与任务在同一事务中写入，失败时不留下半成品。
4. 有余力再进入 3.4 Worker，不强行为了完成阶段而同时铺开后面的模型解析、Embedding 和检索。
5. 每新增一个主要文件，都应该能用一句话说明它的职责；如果主流程再次被边界代码淹没，先简化结构再继续增加功能。

力扣继续低强度保温。课程 Skill 只根据真实学习问题调整，不再花大量时间提前设计万能流程。

## 写在最后

上周，我还在验证“把大型项目拆成课程”是否可行。这周至少证明了一件事：借助课程和隔离重建，我确实可以从技术探针逐步走到正式工程，并跑通一条完整业务链路。

但新的困难也随之出现。技术组件单独理解以后，真正复杂的是怎样把业务实体、状态、持久化和错误边界组织成仍然容易阅读的代码。AI 可以很快补全各种异常处理，也可以生成看起来规范的分层结构，但它不会自动保证这些结构适合我的理解能力和项目当前规模。

接下来，我需要学习的不只是怎样把功能做出来，也包括怎样删掉暂时没有价值的复杂度、怎样让主流程保持可见，以及什么时候应该停止生成代码，先重新整理设计。

阶段 2 已经完成。下周进入阶段 3 的真实业务部分，但推进速度不再只看课时数量，而要看我能不能打开一个目录就知道每个文件负责什么，能不能沿着一条请求完整解释数据怎样变化，也能不能在出现问题时找到应该修改的位置。
