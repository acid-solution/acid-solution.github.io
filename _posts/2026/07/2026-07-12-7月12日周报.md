### 每日内容总结

07/06 为 Todo 项目增加了 User 模型，并学习 bcrypt 的基本用法。数据库里不能直接保存明文密码，而是保存密码哈希。bcrypt 会自动加盐，所以即使两个用户使用相同密码，最终得到的哈希通常也不相同。验证密码时也不能重新哈希后直接比较，而是要使用 bcrypt 提供的比较函数。bcrypt 故意设计得比较慢，也是为了提高暴力猜密码的成本。

07/07 实现了用户注册和登录接口。注册时先对密码进行哈希，再把用户名和密码哈希写入数据库；登录时根据用户名查询用户，再用 bcrypt 校验密码。这次开发时也重新感受了一下代码的依赖顺序，可以从 model、repository、service、handler 自底向上写，也可以先从接口目标出发再逐层补齐，关键是每次只处理一条比较清楚的链路。

07/08 开始实现 Token 和 Session。Access Token 使用 JWT，过期时间较短，主要用于访问 API；Refresh Token 使用随机字符串，过期时间更长，并且只把哈希保存到数据库。登录成功后会创建一条 Session，记录用户、Refresh Token 哈希和过期时间。刷新时会同时生成新的 Access Token 和 Refresh Token，并把旧 Refresh Token 替换掉，这样旧 Token 再次使用时就会失效。

07/09 编写了 Gin 鉴权中间件。请求进入后先从 Authorization Header 中提取 Bearer Token，再解析 JWT，取出用户 ID 和 Session ID，然后查询 Session 是否存在、是否过期以及是否已经撤销。校验成功后，把用户 ID 和 Session ID 放进 Gin Context，后面的 Handler 就可以直接取得当前登录用户。这里也进一步理解了中间件和 Handler 本质上都是处理函数，同一层级主要按照注册顺序进入，`c.Next()` 前后的执行顺序有点像先进后出的调用栈。

07/10 给 Todo 增加了 `user_id`，并把用户条件加入查询、更新和删除操作。这样用户只能看到和操作自己的 Todo。即使知道其他用户 Todo 的 ID，因为查询条件同时要求 ID 和当前用户 ID 匹配，也拿不到其他用户的数据。对于不存在或不属于当前用户的 Todo，接口统一按资源不存在处理，也可以避免暴露其他用户的数据是否存在。

07/11 把注册、登录、JWT、Session、鉴权中间件和受保护的 Todo CRUD 整合到一起，并调整了前端。在自己的浏览器中测试了注册、登录、创建 Todo、查询列表、修改、完成和删除等主要流程，也使用不同账号检查了 Todo 数据隔离。前几天因为感冒发烧没有按原时间完成，周末把这一整条功能链补齐了。

### 自我感悟

这周学到的其实更像是一种思维上的感觉，JWT令牌的实现其实并不复杂，复杂的是整个认证系统的一整条链路：密码需要安全存储，登录后需要生成 Token，后续请求需要鉴权，长期登录需要 Refresh Token，退出登录还需要让 Session 失效。需要综合考虑数据库压力，安全问题，实现和维护的难度，做出一定取舍。

JWT 本身比较适合快速验证请求，但如果只使用完全无状态的 JWT，退出登录后已经签发的 Token 在过期前仍然可能有效。增加服务端 Session，并让鉴权中间件检查 Session 状态，就可以在 Logout 后立即撤销登录状态。不过这样每次鉴权都会多一次数据库查询，之后如果项目继续扩大，可能还需要考虑缓存或者其他会话管理方式。

### 本周刷题收获

1. 杨辉三角每一行的首尾都是 1，中间位置可以由上一行相邻的两个数相加得到。重点是处理好每一行的长度和边界。
2. 搜索二维矩阵 II 可以从右上角或者左下角开始搜索。每比较一次，都可以排除一整行或者一整列，比对每个位置逐个搜索更高效。
3. 只出现一次的数字利用了异或的性质：相同数字异或后为 0，任何数字和 0 异或仍然是自己。遍历一遍数组就能得到只出现一次的数字。
4. 环形链表 II 在判断有环的基础上，还需要找到环的入口。我直接使用map记录了走过的节点。但是快慢指针可能是更好的选择。
5. 多数元素使用摩尔投票降低额外空间。摩尔投票的核心是让不同元素互相抵消，最后留下的候选值就是多数元素，但前提是题目保证多数元素一定存在。

### 接口列表

```text
POST   /api/register         注册用户
POST   /api/login            用户登录
POST   /api/refresh          刷新 Access Token 和 Refresh Token
POST   /api/logout           退出当前登录，需要鉴权

POST   /api/todos            创建当前用户的 Todo，需要鉴权
GET    /api/todos            查询当前用户的 Todo，需要鉴权
PUT    /api/todos/:id        更新当前用户的 Todo，需要鉴权
PATCH  /api/todos/:id/done   标记当前用户的 Todo 完成，需要鉴权
DELETE /api/todos/:id        删除当前用户的 Todo，需要鉴权
```

### 请求链路

```text
用户在前端登录
↓
POST /api/login
↓
Handler 绑定用户名和密码
↓
Service 查询用户并使用 bcrypt 校验密码
↓
创建 Session，生成 Access Token 和 Refresh Token
↓
Refresh Token 哈希写入 MySQL
↓
前端保存登录凭证
↓
请求 Todo 接口时携带 Authorization: Bearer <access_token>
↓
鉴权中间件解析 JWT 并检查 Session
↓
用户 ID 和 Session ID 写入 Gin Context
↓
Handler 取得当前用户 ID
↓
Service 处理业务逻辑
↓
Repository 使用 id 和 user_id 操作 MySQL
↓
返回当前用户自己的 Todo 数据
```

### 项目收获

这周 Todo 项目从一个工程化的单用户 CRUD，进一步变成了有注册、登录、会话管理和权限隔离的小型 Web 项目。功能本身仍然不算复杂，但认证和权限链路涉及的模块明显更多，必须把 Handler、Service、Repository、Middleware、Model 和配置连接起来。

现在对“登录成功”这件事的理解也比以前具体了一些。它不只是返回一个 Token，还包括密码如何保存、Token 如何过期、长期会话如何刷新、退出登录如何撤销，以及每一次业务查询怎样确定当前用户。把这些内容真正放进项目之后，之前比较抽象的认证概念开始能够对应到具体代码了。
