从 6 月 1 日开始，我给自己安排了一轮低强度的“求职保温”学习。那段时间的主线仍然是科研，所以这轮计划并不是要在两个月内把后端和面试知识全部学完，而是希望在不影响论文的前提下，重新保持写代码和做算法题的手感，同时把技术方向从原来更熟悉的 C++ 逐渐扩展到 Go 后端。

到 7 月 25 日，我决定正式结束这轮学习。回头看，它最终并不只是让我“学了一点 Go”：我从基础语法一路写到了一个包含 MySQL、Redis、用户认证、权限隔离和 Docker Compose 的 Todo 项目，也对怎样借助 AI 学习、怎样安排项目型任务有了更具体的认识。

这篇文章综合了滴答清单里的每日记录、前六篇周报、Todo 仓库的源码和 Git 提交历史，是对这一阶段的一次完整复盘。

## 七周里，学习路线是怎样推进的

整个过程不是先把一套 Go 教程完整看完，再开始做项目，而是每学到一部分，就尽快把它接进同一个 Todo 项目。项目大致经历了下面这条演进路线：

```text
Go 环境与基础语法
        ↓
net/http 与 Gin 接口
        ↓
内存版 Todo Demo
        ↓
MySQL 持久化与分页筛选
        ↓
GORM、配置、日志、错误码与项目分层
        ↓
注册登录、JWT、Session 与多用户隔离
        ↓
Redis 列表缓存与缓存失效
        ↓
Docker 多阶段构建与 Compose 编排
```

### 第一阶段：从“会别的语言”切换到 Go 的思路

前两周主要学习 Go 基础，包括变量、函数、包、slice、map、struct、method、receiver、error、interface、pointer、defer、panic、recover、goroutine、channel 和 context。

因为我以前写过 C++、Java 和 Python，所以基础语法上手并不难，真正需要适应的是 Go 自己的设计习惯。例如：

- Go 的函数传参始终是值传递，slice、map 等类型只是复制后的值仍然指向底层数据；
- 接口不需要显式声明实现，更适合按使用方需要定义小接口；
- error 是普通返回值，需要逐层处理并补充上下文；
- goroutine 负责并发执行，channel 负责通信，context 负责控制一条任务链的生命周期；
- Go 更强调组合，而不是传统面向对象里的继承。

这两周的最大作用，是让我后面读项目代码时不再只会照着写，而是开始理解为什么 Handler、Service、Repository 之间要这样传对象、传 context 和返回 error。

### 第二阶段：从 HTTP 接口到第一个可用 Demo

第三周开始接触 `net/http` 和 Gin。我先写了最简单的 `/ping`，然后逐步学习路由、参数绑定、JSON 响应、HTTP 状态码和统一响应结构，最后用内存 map 做出了一个 Todo Demo。

这个版本已经能完成 Todo 的创建、查询、更新、完成和删除，也托管了一个简单前端。虽然所有逻辑还挤在少量文件里，数据重启后也会消失，但它第一次把完整请求链路串了起来：

```text
浏览器操作
→ HTTP 请求
→ Gin 路由
→ 参数绑定与校验
→ 业务处理
→ JSON 响应
→ 页面刷新
```

和以前使用 Spring Boot 的感受相比，Go + Gin 把许多步骤直接摆在代码里，初期确实更容易看清一次请求究竟经过了什么。

### 第三阶段：让数据真正保存下来

第四周开始接 MySQL。我先复习建表和基础 SQL，再用 `database/sql` 把 Todo 的增删改查、完成状态筛选和分页接入数据库。

这部分让我重新熟悉了 `Exec`、`QueryRow`、`Scan`、`RowsAffected`、`LIMIT` 和 `OFFSET` 等内容。列表接口也从只返回数组，变成同时返回 `page`、`page_size`、`total` 和 `total_pages`。

项目到这里才从“能演示的内存 Demo”变成了“数据能够持久化的小型 Web 项目”。同时我也发现，SQL 语法本身并不是最难的，真正容易出问题的是接口参数、空结果、错误转换、分页边界和返回结构怎样一起配合。

### 第四阶段：从功能能跑到结构能看

第五周把手写 SQL 版本改成了 GORM，并开始做工程化整理：

- 配置通过环境变量读取；
- 使用 `.env` 管理本地开发配置；
- 使用 `slog` 记录结构化日志；
- 为请求生成 `request_id`；
- 统一参数错误、资源不存在和服务端错误；
- 拆分 handler、service、repository、model、response、config 等目录。

这次重构并不顺利。我一开始一次性创建并修改了很多文件，结果依赖关系全部乱掉，只能撤回。后来改成按照依赖顺序逐层调整，每完成一小步就编译一次，让报错帮助我定位下一处修改，过程反而稳定了很多。

这是这轮学习里一个很重要的经验：**工程化不是多建几个目录，而是让依赖方向、错误流转和职责边界变得可理解。**

### 第五阶段：把登录真正接进业务

第六周增加了用户注册、登录和权限隔离，主要完成了：

- bcrypt 密码哈希；
- JWT Access Token；
- 随机 Refresh Token 及哈希存储；
- 服务端 Session、Token 轮换和退出撤销；
- Gin 鉴权中间件；
- Todo 增加 `user_id`；
- 查询、修改和删除都同时校验当前用户；
- 前端注册、登录和认证请求。

以前我会把“登录成功”简单理解成服务端返回一个 Token。真正做完后才发现，一条完整认证链路还要考虑密码如何保存、长期登录如何刷新、退出后怎样立即失效，以及每次访问业务数据时怎样确认数据属于当前用户。

这一周还因为感冒发烧打乱了节奏，但后面把注册、登录、刷新、退出和受保护 Todo CRUD 整体串了起来，并用不同账号检查了数据隔离。

### 第六阶段：缓存与容器化收尾

最后一段学习围绕 Redis 和 Docker 展开。

Todo 列表缓存使用 Redis String 保存 JSON。缓存 key 包含用户、页码、每页数量和完成状态，避免不同查询条件互相污染：

```text
todo:list:user:{userID}:page:{page}:size:{pageSize}:completed:{status}
```

查询时先读 Redis，未命中再回源 MySQL 并写入缓存；创建、更新、完成或删除 Todo 后，则让当前用户的列表缓存失效。这个过程让我意识到，缓存并不只是会写 `Get` 和 `Set`，还必须同时考虑 key 设计、TTL、数据一致性、穿透、击穿和雪崩。

之后我又编写了多阶段 Dockerfile，并用 Docker Compose 编排 API、MySQL 和 Redis。这里也遇到了一个很典型的问题：AI 最初给出的 Dockerfile 没有把前端静态文件复制进运行镜像，导致后端能启动但页面无法使用。最后还是要自己阅读构建过程并补上静态资源。

## 最终的 Todo 项目做到了什么

[Todo 项目仓库](https://github.com/acid-solution/go-todo)

截至 7 月 22 日，仓库当前包含 25 个 Go 源文件，主要功能包括：

- 用户注册、登录、刷新令牌和退出登录；
- JWT 与服务端 Session 鉴权；
- 多用户 Todo 数据隔离；
- Todo 增删改查、完成状态、分页与筛选；
- MySQL + GORM 数据持久化；
- Redis 列表缓存和写操作后的缓存失效；
- 配置读取、统一响应和结构化请求日志；
- Docker 多阶段构建；
- Docker Compose 启动 API、MySQL 和 Redis。

它已经达到了这轮学习项目的目标：能够把一次请求从路由、鉴权、业务逻辑、数据库、缓存一路追下去，也能解释主要技术选型解决了什么问题。

但它仍然只是一个后端学习项目，而不是成熟的生产系统。目前仓库没有自动化测试和 CI；缓存失效使用模式匹配扫描，更适合当前 Demo 的数据规模；监控、异步任务、限流、接口文档和更完整的异常场景也没有补齐。前端主要用于功能验证，同样不是项目重点。

明确这些边界很重要。这个项目的价值不是证明我已经精通 Go 后端，而是让我建立了一个可运行、可阅读、可以继续改造的后端基础模板。

## 力扣：目标是保持手感，不是追求题量

这轮学习里，38 个日常任务留下了明确题号或题目链接，去重后至少涉及 35 道不同题。内容覆盖链表、数组、矩阵、二叉树、哈希、滑动窗口、前缀和、动态规划、二分和位运算等常见类型。

相比题目数量，我更在意几次形成联系的过程：

- 通过 53 和 560，把最大子数组和、前缀和以及历史状态之间的关系串了起来；
- 通过多道链表题，逐渐熟悉快慢指针和节点引用；
- 通过矩阵旋转、矩阵置零等题，意识到空间优化经常来自复用原数据结构；
- 通过二叉树题，重新熟悉递归函数的含义和边界。

这部分训练显然还不足以支撑正式面试，但完成了“不要让算法手感完全中断”的目标。没有完成的最后几次八股和补题，也不需要被包装成成果。

## 这套 AI 学习工作流，哪里有效，哪里失效

最开始，我用 Codex 根据个人背景拆学习计划，再通过滴答清单安排到每天；学习时让 AI 生成文字材料，遇到问题随时追问；完成后把关键内容写回任务描述，周末再整理成周报。

在基础知识阶段，这套方法非常有效。AI 可以根据我已经会 C++、Java 和 Python 的背景，重点解释 Go 的差异，也省去了大量寻找合适入门资料和安排每日进度的时间。

但项目复杂以后，问题也逐渐暴露：

1. **AI 容易失去项目上下文。** 代码量增加后，它可能重复造结构、忽略已有约定，甚至引入新的错误。
2. **教程顺序不等于项目顺序。** 原计划可能要求先学知识再改代码，AI 却直接跳进实现，导致前置知识和实际进度错位。
3. **一次性改太多很危险。** 工程化重构时，必须依靠小步修改、编译检查和 Git 回退，而不是相信一次生成就能完成。
4. **最终责任仍然在人。** 无论是认证设计、缓存 key，还是 Docker 静态资源遗漏，都需要我理解代码后才能发现和修正。

所以我现在更愿意把 AI 当作一个随时可以讨论的搭档，而不是自动驾驶。它可以帮助我查资料、解释概念、生成初稿和定位问题，但不能替代我建立代码的整体模型。

## 为什么这轮学习到这里就结束

最后 10 项任务原本用于补 Go、MySQL、Redis、HTTP/TCP 八股，以及整理周报、项目讲解和下一阶段入口。它们并不是毫无价值，但继续完成它们的边际收益已经不高。

这轮计划最初只要求我在科研主线之外保持求职学习，并完成 Go 环境、后端入门和少量算法训练。实际结果已经向前走了不少：我不仅跑通了 Go，还提前做出了一个覆盖 API、数据库、缓存、鉴权、配置、日志、错误处理和 Docker 的后端模板。

与其为了清空列表重复复盘，不如承认这一轮已经结束。未完成的内容如果以后真的影响项目讲解或面试，再在新的阶段按实际问题重新创建任务，而不是继续背着旧计划前进。

## 写在最后

七周前，我对 Go 的理解主要停留在“语法看起来不复杂”；现在，我至少已经亲手走过了一个小型后端从内存 Demo 到持久化、工程化、认证、缓存和容器化的过程。

更重要的是，我开始能区分“代码跑起来”“项目结构能看懂”和“系统足够成熟”这三个不同层次。Todo 项目目前只完成了前两个的一部分，离真正能经受连续追问的工程项目还有距离，但它已经成为下一阶段继续学习的可靠起点。

这轮学习到这里正式收尾。48 项完成，10 项主动终止，不追求一个好看的全勾数字，也不把没有做过的内容算进成果。留下来的代码、提交记录和复盘文章，比完成率更能说明这段时间究竟学到了什么。
